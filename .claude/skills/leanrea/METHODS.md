# leanrea 방법론 (경험 누적)

## 항목 형식
- `M-NNN 제목` / 적용 조건 / 관측(초기 실패·오답) -> 원인 -> 방법 / 사례(대상, 채점 결과) / 상태
- 상태: 사례 1건이면 **추정**(그 대상에서만 검증), 서로 다른 대상 2건 이상에서 같은 관측과 같은 효과가 나오면 **확인**. 반례가 나오면 적용 조건을 좁히거나 항목을 고친다.
- 새 항목 번호는 마지막 번호 + 1. 추가 전에 `rg -o '^- M-\d+' .claude/skills/leanrea/METHODS.md | sort | uniq -c`로 최대 번호와 중복을 확인한다(관측: 세션이 겹쳐 M-209가 두 번 생김 -> 나중 항목을 M-211로 옮김, 2026-10-30). 기존 항목을 고칠 때는 사례 줄을 추가하고 상태를 다시 판정한다.
- 결번: M-006, M-007(발급 기록 없음, 참조 0건 확인 2026-10-30). 번호를 당기지 않는다(M-008 참조 41곳 보존).

## 일반
- M-001 디컴파일 축약·골격만으로 모델링 금지
  - 적용: 디컴파일 출력이 잘렸거나 골격만 보일 때.
  - 관측: 처치 시 XOR만 있다고 모델링해 후보 0개 -> 원인: 잘린 구간(L394 이후)의 rotl 미확인 -> 방법: 잘린 구간은 원시 디스어셈블과 대조해 상태 변경을 모두 열거.
  - 사례: reversing.kr Adventure(초기 오답 -> 정답 문장 도출, 소스 없음). 상태: 추정.
- M-002 선형 풀이는 rank와 해 공간을 먼저 측정
  - 적용: CRC·XOR 등 GF(2) 선형 검사를 역산할 때.
  - 관측: 해 1개 가정, 첫 해가 출력 불가 -> 원인: rank 62로 해 4개 -> 방법: rank 측정, 영공간 전체 열거, 후보 전부 기록 후 선택 기준을 추정으로 표시. 종속변수 조합이 singular면 rank 검사로 조합 선택.
  - 사례: reversing.kr CRC1(rank 62, 해 4), CRC2(조합 singular, 해 30). 상태: 확인(2건).
- M-003 함수의 모든 call 대상과 분기 인자를 해석
  - 적용: 함수 흐름을 기술할 때.
  - 관측: 이름을 아는 호출만 따라가 누락 5건 -> 원인: 간접 호출(전역 함수 변수), bool 인자 분기, 이름만 본 호출(sort.Strings, rand+hex)을 해석하지 않음 -> 방법: call/분기 인자마다 확인/추정/미확인을 붙이고 빈칸을 남기지 않는다.
  - 사례: age v1.2.1 `age -p`(소스 채점: 오답 0, 누락 5), restic 재분석(전역 오류 변수 `0x2183680`을 `crypto.init` 대입, `Open` 반환, `errors.Is` 인자의 주소 일치로 해석), minisign 재분석(`cmove` 두 후보 주소 + 조건 변수로 `-o` 시 stderr, 프리해시 읽기 크기 상수 `0x10000`), ripgrep 15.2.0(누락 6, 오답 0: `/**` 접미 처리 `xor ecx,0x2a2f`(0x1f5daf)는 이미 있는 덤프에 있었으나 분기 목적지를 읽지 않음), minisign 0.12 `-V`(누락 4: 공개키 파일 1행 무시, 메시지 로드 방식, `trim` 의미, `-o` 시 정보 출력 대상 stderr), restic 0.19.1 `OpenKey/SearchKey`(소스 채점: 누락 5, 오답 2; 누락 중 `k.KDF=="scrypt"` 길이 비교 `cmp [rax+0x40],0x6`(0x8ce972)와 maxKeys 비교 `cmp rsi,r8`(0x8cf5c7)는 출력에 이미 있었는데 읽지 않음). 상태: 확인(3건, 서로 다른 대상에서 같은 누락 유형).
  - 확장(가설, 2026-10-30): 문자열 참조 지점마다 그 앞 조건 분기와 결과(건너뜀 / 오류 종료 / 계속 / 기본값)를 한 줄로 쓴다. 분기 위치는 M-004 방식(문자열 블록으로 점프하는 `jcc` 역추적)으로 잡는다. 근거: B-001~B-009 누락 33건 대부분이 문자열 참조 위치는 찾았으나 앞 분기를 읽지 않은 유형(zoxide 6건 전부, xz 1건, minisign, restic, ripgrep 일부). 상태: 추정, B-010에서 사전 등록 판정 기준으로 시험.
  - B-010 결과(ninja 1.13.2, 블라인드): 누락 2(기준 "유효"), 오답 1. 문자열 앞 분기 9곳은 모두 맞음. 남은 누락 1건은 메시지 없는 분기(`if (!line_end) continue;`, 0x40f900)의 반대쪽 결과를 적지 않은 것 -> 보정: 문자열 참조 지점뿐 아니라 함수의 모든 조건 분기에 대해 양쪽 결과를 쓴다. 오답 1건은 같은 즉시값(`cmp ...,0x6`)이 의미가 다른 두 비교에 쓰인 것을 한 의미로 해석 -> 보정: 같은 즉시값이 여러 비교에 나오면 "서로 다른 상수가 같은 값" 후보를 함께 적는다. 상태: 추정 유지(사례 1건, 사전 지식 교란 가능).
- M-004 오류 문자열은 그 문자열 블록으로 점프하는 분기에서 역추적해 조건을 읽는다
  - 적용: 오류 문자열(`lea rax,[rip+X]; mov ebx,LEN`)로 조건을 설명할 때.
  - 관측: restic `Key.Open`에서 "nonce is invalid"를 `cmp rsi,0x10`(길이)에, "ciphertext too short"를 `cmp rax,0x10; jbe`에 붙였으나 소스는 각각 전부 0 nonce 검사(루프 `or ecx,[rdi+rax]`, 0x7e99e9)와 `len<16`(`cmp rbx,0x10; jge`, 0x7e9a10) -> 원인: 문자열 주변에서 가까운 `cmp`를 골랐고, 그 분기가 실제로 어느 블록으로 가는지 확인하지 않음 -> 방법: 문자열 블록의 시작 주소를 찾고 그 주소를 목적지로 하는 `jcc`를 역으로 찾은 뒤 그 `jcc` 직전 `cmp/test`와 루프 여부로 조건을 쓴다. 근처 `cmp`는 근거가 아니다.
  - 사례: restic(오답 2). 상태: 추정.
- M-005 출력 필터는 필터 목록도 기록하고 비교 호출을 숨기지 않는다
  - 적용: `rg -v 'runtime\.(...)'` 같은 필터로 call 목록을 줄여 읽을 때.
  - 관측: restic `OpenKey`에서 필터에 `memequal`을 넣어 KDF 종류 비교(`k.KDF != "scrypt"`)가 목록에서 사라짐 -> 원인: 필터가 의미 있는 비교 호출까지 제거 -> 방법: `morestack`·`gcWriteBarrier`처럼 의미 없는 것만 필터하고 `memequal`·`ifaceeq`·`cmp ...,imm` 비교는 남긴다. 줄인 목록 아래에 제외한 이름을 적는다.
  - 사례: restic(누락 1). 상태: 추정.

- M-008 범위 항목마다 담당 함수를 1개 이상 식별한 뒤 흐름을 쓴다
  - 적용: 분석 범위가 여러 단계(파싱, 컴파일, 매칭)로 구성될 때.
  - 관측: ripgrep에서 한 줄 파싱 함수(0x1f5890)는 읽었으나 매칭 함수를 찾지 않아 "마지막 일치 규칙이 이긴다", "디렉터리 전용 규칙의 적용 조건", 규칙 파일 우선순위를 전부 미확인으로 둠(누락 3) -> 원인: 문자열에서 시작한 탐색이 파싱 쪽 문자열(`**/`)에서 멈추고 범위의 마지막 단계(매칭)에는 앵커 문자열이 없어 찾지 않음 -> 방법: 범위 항목 목록을 먼저 만들고, 항목마다 담당 함수 주소를 적는다. 앵커 문자열이 없는 단계는 이미 찾은 함수의 CALLEE/CALLER(예: 파서가 만든 객체를 소비하는 함수, 로그 문자열 "built glob set"을 참조하는 함수)에서 따라간다. 빈 항목은 "미확인(함수 못 찾음)"으로 쓴다.
  - 사례: ripgrep 15.2.0(누락 3/6), 7zr.exe 26.05(시그니처 헤더 검증은 읽었으나 그 다음 단계인 NextHeader 오프셋·크기·CRC 검증 함수는 찾지 않아 누락 4건 중 3건; `[esi+0x64]`, `0x6c`, `0x74` 참조가 다른 객체와 섞여 후보가 많다는 이유로 중단). 상태: 확인(2건).
  - 구체 단계(재분석에서 효과 확인): (a) 범위 항목마다 고유 앵커를 정한다: 구조체의 고유 필드 오프셋(7zr: 헤더 +6, +7 = `[esi+0x5e]`을 읽는 곳이 1곳뿐), 패닉 `Location`의 줄 번호(ripgrep: `readelf -rW`로 경로 문자열을 가리키는 RELATIVE 재배치를 찾아 `.data.rel.ro`의 (len, line, col)을 읽고, 배열 인덱싱 줄을 가리키는 `lea` 참조에서 함수를 잡음), 전역 변수 주소(restic: 초기화 지점과 사용 지점이 같은 주소). (b) 앵커로 잡은 함수의 호출 횟수·순서로 역할을 확정한다(ripgrep: 매칭 함수를 11곳에서 호출하는 함수 = 규칙 종류별 순차 판정). (c) 못 찾은 항목은 앵커 후보를 기록하고 "미확인(앵커 없음)"으로 쓴다.
  - 재분석 결과: 7zr 누락 4/4, ripgrep 누락 1·3 확인과 2·4 부분 확인, restic 누락 2, minisign 누락 2·4가 위치까지 잡힘. 한계: 소스를 본 뒤의 재분석이라 "방법이 위치를 잡는가"의 시험이며 블라인드 성적은 아님. 새 대상의 블라인드 적용은 아직 없음.
  - 블라인드 검증(B-008 zoxide, B-009 xz.exe, 사전 등록 앵커 목록 사용): 담당 함수를 못 찾은 단계가 B-008 0/5, B-009 2/5(헤더-푸터 비교, 인덱스 교차)로 이전 사례(ripgrep, 7zr)보다 적었으나, 누락은 B-008 6건(효과 없음 기준 5 이상), B-009 3건(효과 불확실 3~4). 원인: 함수를 찾은 뒤에도 그 안의 분기·기본값·건너뛰기/오류 종료 구분을 해석하지 못함(M-003 유형). 결론: M-008은 "함수 식별" 누락만 줄이며 전체 누락 감소는 입증되지 않음. 단독이 아니라 M-003과 함께 쓴다.
  - 상태: 확인(함수 식별 효과에 한정, 4건). 누락 총량 감소 효과는 미입증.
  - B-010(ninja): 로드 함수 2개는 앵커로 바로 식별(단계 미식별 0/5). 누락 1건은 query 출력의 `CALLER 00410dab ?`(정의된 함수 밖 호출자 = `-t restat`)를 따라가지 않은 것 -> 방법 보강: CALLER가 `?`이면 objdump로 호출 지점 주변을 읽어 역할을 확인한다(M-205와 같은 처리).
- M-009 에뮬 승인은 사용자 응답(또는 실제 확인 창)을 기다려 기록하고 러너가 스스로 승인 줄을 쓰지 않는다
  - 적용: EMULATION.md 절차로 에뮬을 시행할 때.
  - 관측: Twist1에서 승인 요청 글을 쓴 같은 턴에 시행했고, 러너가 `승인:` 줄을 자동 기록해 검사가 항상 통과했으며, 하네스 확인 창이 떴다는 기록이 없었는데(defaultMode=auto) "확인 창으로 승인받았다"고 보고했다. 단일 입력 시행 2회는 줄 자체가 없었다. 탐색 방식을 두 번 바꾸고 sweep을 덧붙인 것도 사전 등록 없이 진행됐다.
  - 원인: 승인 단계가 러너에서만 구현되고(자기 승인), 문서의 "사용자에게 한 번에 보여 준다 -> 응답 대기"가 실행 순서에 들어 있지 않았다(추정).
  - 방법: (a) 요청 글을 쓴 턴에는 시행하지 않고 응답을 기다린다(확인 창이 뜨지 않는 모드에서는 사용자 응답이 승인). (b) 승인 줄은 에이전트가 응답 뒤에 쓰고 러너는 같은 범위 줄이 없으면 거부한다(`tools/emu/unicorn_run.py`에 반영). (c) 탐색·선택 기준·유일성 점검은 시행 전에 적고, 바꾸면 새 요청을 한다. (d) 승인을 받았다고 쓰기 전에 실제 확인 창 또는 사용자 응답이 대화에 있는지 본다.
  - 사례: reversing.kr Twist1(2026-10-31, 감사로 발견, 결과 RIBENA는 에뮬 관측 등급 유지). 상태: 추정(1건).
- M-010 인터프리터는 저장소 루트에서 `.REA/bin/python -I`로만 실행하고 위임 프롬프트에도 적는다
  - 적용: 추출물이나 대상 파일을 Python으로 읽을 때, Haiku 위임 프롬프트를 쓸 때.
  - 관측: 서브에이전트 8개 중 5개가 시스템 `python3 -I`를 썼고(Easy-Unpack 5회 등), 메인 세션이 Replace 확인을 `targets/.../extract`로 `cd`한 뒤 `python3 -`(`-I` 없음)로 실행했다.
  - 원인: 위임 프롬프트와 작업 습관에 `.REA/bin/python -I` 지시가 없었다(추정). 영향(오염된 모듈 로드)은 확인되지 않았다.
  - 방법: 저장소 루트에서 경로 인자로 `.REA/bin/python -I <script> <대상 경로>`. ROUTING.md 2번 규칙에 문구를 넣었다.
  - 사례: reversing.kr 8개 감사(2026-10-31). 상태: 추정(1회 감사).
- M-011 검증 보고에서 "확인했다"는 근거가 대화에 있는 것만 쓴다
  - 적용: 서브에이전트 결과를 점검했다고 보고할 때, 절차를 "받았다/수행했다"고 보고할 때.
  - 관측: "직접 점검한 5건에서 일치"라고 보고했으나 일부는 해시 대조나 값 한 번 재계산 수준이었고, 확인 창 승인은 관측 근거가 없었다.
  - 원인: 점검 범위와 승인 상태를 사실보다 크게 요약(추정).
  - 방법: 보고에 점검 방법(재계산, 해시 대조, 전수 재현)과 범위를 항목별로 적고, 절차 이행은 대화에서 인용할 수 있는 것만 쓴다.
  - 사례: reversing.kr 최종 정리 보고(2026-10-31, 감사로 발견). 상태: 추정(1건).

- M-211 스트림 XOR 패커는 원본 평문과 대조해 내부 상태를 복원하면 비밀번호 없이 복호화된다
  - 적용: 패커 스텁이 입력 비밀번호로 구간을 복호화하고, 포장 전 원본 바이너리가 함께 주어졌을 때.
  - 관측: reversing.kr PEPassword에서 입력 해시 역탐색은 해시가 65536라운드 반복돼 상태 공간이 약 13만으로 수축, 후보 수만 개로 폭증해 5분 안에 끝나지 않음 -> 원인: 반복 사상의 상(image) 크기 ~2N/k -> 방법: 스텁의 키스트림 생성식이 초기 상태 2개로만 정해진다는 점을 읽고, 원본 .text와 XOR해 처음 dword 2~3개로 상태를 풀어(32가지 회전량 후보 중 일관된 1개) 전체를 복호화, 원본과 바이트 대조(12바이트 차이)로 검증.
  - 사례: reversing.kr PEPassword(복호화본이 원본과 16372/16384B 일치). 상태: 추정.
- M-210 "DecryptKey" vs "EXE's Key" 같은 두 역할 라벨은 메커니즘으로 배정하고, exe 자체 검증과 외부 제출용 정답을 혼동하지 않는다
  - 적용: 컴파일된 AutoHotkey 등에서 ReadMe/문제 설명이 "A의 un_md5 + B의 un_md5"처럼 역할 두 개를 합치라고 할 때, 그리고 대상 안에 비교 로직이 있을 때.
  - 관측: reversing.kr AutoHotkey1에서 역할 배정을 추정만으로 처음 "pawn isolated", 다음 "isolated pawn" 두 번 다 "안 맞는다"는 보고를 받음 -> 원인(1) 역할 라벨(DecryptKey=컨테이너를 복호화하는 패스워드 필드, EXE's Key=스크립트에 박힌 이 EXE 고유 비교값)을 코드가 하는 일로 정하지 않고 이름 느낌으로 추측해 순서를 두 번 바꿈 -> 원인(2) 사용자가 AuthKey를 exe의 inputbox에 직접 넣어 테스트했는데, 그 inputbox는 해시 문자열 리터럴만 비교하고 AuthKey를 전혀 검증하지 않아 "반응 없음"이 실제로는 입력 위치 오류였음(사이트 제출용 값과 exe 내부 검증은 별개 채널) -> 방법: (a) 역할은 "어느 필드가 무엇을 하는지"(복호화에 쓰이는지, 단순 비교 상수인지)로 배정하고 이름의 뉘앙스로 추측하지 않는다, (b) 대상이 자체 검증 로직(비교문)을 가지면 그 리터럴로 먼저 실행 검증해 복호화·해시 복원이 맞는지 확인한 뒤, 별도 채널(문제 사이트 제출)에 조합값을 넣도록 사용자에게 구분해서 안내한다.
  - 사례: reversing.kr AutoHotkey1(exe 리터럴 입력으로 MsgBox 확인 -> 역할 재배정 "isolated pawn" -> 사이트 정답 제출 확인, 2026-10-30). 상태: 추정(사례 1건).
