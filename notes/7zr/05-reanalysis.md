# 7zr 재분석 (M-008: 범위 후반 단계 담당 함수 식별)

## 방법
- 관측: 앞선 분석에서 `[esi+0x64]`, `0x6c`, `0x74` 참조를 넓은 구간(0x440000~0x452000)에서 찾아 후보가 너무 많아 중단했다.
- 조치(M-008): 시그니처 헤더는 객체의 `[esi+0x58]`에 복사된다(0x44daae, 0x44dc00). 헤더 안의 오프셋이 유일한 필드를 먼저 찾는다. 버전 바이트는 헤더 +6, +7 = `[esi+0x5e]`, `[esi+0x5f]`. `rg '\[...\+0x5e\]'`로 읽는 곳이 단 1곳(0x44fa10, 0x44fa1b)이었다.
- 결과: 그 지점의 함수(SEH 프롤로그 `mov eax,0x47b188; call 0x471a60`, 시작 0x44f9df)가 다음 헤더 처리 담당 함수로 확정.

## 누락 4건의 위치 (함수 0x44f9df, 반환 `ret 0x14`)
| 누락 | 바이너리 근거 |
|---|---|
| 3. 버전 메이저 검사 | 0x44fa10에서 `[esi+0x5e]`를 읽어 `cmp BYTE PTR [eax],0x0`(0x44fa1e), 불일치면 `jne 0x44fc91` -> `push 1; pop eax` 반환 1. 마이너(`+0x5f`)는 0x44fa1b에서 읽지만 비교 없이 저장 |
| 1. 다음 헤더 정합성 | 오프셋 상위 32비트 `cmp DWORD PTR [ebp-0x10],0x40000000; ja 0x44fc91`(0x44fbbb, 0x44fbc8) 및 같으면 하위 `test edx,edx; jae`(0x44fbd0); 크기 상위 `cmp ecx,0x10000; ja`(0x44fbdb), 같으면 하위 `test ebx,ebx; ja`(0x44fbe9) -> 오프셋 >= 2^62 또는 크기 > 2^48이면 반환 1 |
| 2. 크기 0 | `or eax,ebx/ecx; jne 0x44fc2e`(0x44fbf8~0x44fbfc) 아니면 `or edx,[ebp-0x10]; jne 0x44fc91`(오프셋 != 0 이면 거부), `cmp DWORD PTR [ebp+0x8],0x0; jne 0x44fc91`(다음 헤더 CRC 인자 != 0 이면 거부), 통과 시 `mov BYTE PTR [edi+0x148],0x1`(유효 아카이브 플래그) 후 0 반환(0x44fc07~0x44fc2c) |
| 4. 범위 검사와 CRC | 크기 != 0: `HeadersSize += size`(0x44fc3e), 파일 끝까지 남은 크기 `[esi+0x48]-[edi+0x108]` 와 `오프셋+크기` 비교(0x44fc6d~0x44fc88), 부족하면 `mov BYTE PTR [edi+0x14b],0x1` 후 반환 1(0x44fc8a). 충분하면 0x44fca5로: Seek(`call [ecx+0x10]`), 읽기(`call 0x410b79`, 0x44fcee), `call 0x471330` 후 `cmp eax,[ebp+0x8]`(0x44fd03~0x44fd08) 불일치면 `call 0x44d84e`(예외 던짐 함수로 추정), 이후 첫 ID 바이트 `0x01`(kHeader)/`0x17`(kEncodedHeader) 분기(0x44fd52, 0x44fd5b) |
| (보너스) 복구 경로 | 시작 CRC와 오프셋·크기·CRC가 모두 0이면 파일 끝 512바이트(`0x200`) 스캔: `cmp al,0x17` + 다음 바이트 6, `cmp al,0x1` + 다음 바이트 4(0x44fb1f~0x44fb39) |

## 판정
- 4건 모두 위치와 조건을 바이너리에서 확인했고 소스(in:1632-1740)와 일치. **잡힘**. 추가로 소스에서 본 복구 경로(`FORMAT_7Z_RECOVERY`)도 같은 함수에서 식별.
- 보정: M-008에 "범위 항목의 고유 필드(오프셋이 유일한 필드)를 먼저 grep한다"를 구체 단계로 추가.
