# 흐름: 스트림 -> 32바이트 시그니처 헤더 읽기 -> 후보 검증 -> (필요 시) 앞쪽 탐색

## 단계 1: 열기 진입 0x44dd1f
- 관측: 상태 필드 `[esi+0x78],[esi+0x7c]`를 0으로 초기화, 이전 스트림 해제 호출(0x44dd67), 스트림 현재/전체 위치 조회(0x410aa3, `esi+0x40`·`esi+0x48`에 저장), 시그니처 처리 함수 0x44da99 호출, 반환 0이면 0x4100f6(스트림 참조 보관)을 호출하고 0 반환 (0x44dd2a~0x44dd61).

## 단계 2: 시그니처 헤더 읽기 0x44da99
- 관측: `push 0x20; ...; call 0x410b79`(0x44daae~0x44dab5)로 32바이트를 `[esi+0x58]`에 읽음. 읽기 실패(반환 비0)면 그 값을 반환(0x44dc44).
- 관측: 0x44dcbe(후보 검증) 호출, 참(`al`≠0)이면 `xor eax,eax`로 성공 반환(0x44dac4~0x44dacf).
- 관측: 거짓이면 매개변수 `[ebp+0xc]`(최대 탐색 크기로 추정, 64비트)가 null이거나 값이 0이면 `push 1; pop eax`로 1 반환(0x44dad4~0x44dae5) -> 결과(추정): 앞쪽 탐색 허용량이 0이면 "찾지 못함" 코드 1.

## 단계 3: 후보 검증 0x44dcbe (32바이트 헤더)
- 관측: 바이트 2,3,5,4,1,0을 `0xbc,0xaf,0x1c,0x27,0x7a,0x37`과 비교(0x44dcc1~0x44dce2). 하나라도 다르면 `xor al,al`(0x44dd1b) -> 결과: 6바이트 시그니처 `37 7a bc af 27 1c` 일치 필요.
- 관측: `push 0x14; lea ecx,[esi+0xc]; pop edx; call 0x471330`(0x44dce4~0x44dcea) 후 `cmp eax,[esi+0x8]`: 오프셋 12부터 20바이트의 해시(CRC32로 추정, 호출 19곳)를 오프셋 8의 4바이트와 비교 -> 같으면 `al=1` 반환(0x44dcf4).
- 관측: 다르면 오프셋 8~31이 모두 0인지 순회(`cmp BYTE PTR [eax+esi],cl`, 0x44dcfd~0x44dd06). 하나라도 0이 아니면 거짓(0x44dd1b). 모두 0이면 버전 바이트 `[esi+6]`, `[esi+7]`가 둘 다 0이면 `eax=0`(거짓), 아니면 `eax=1`(참) (0x44dd08~0x44dd1a).
- 결과(추정): 헤더 레이아웃 = 시그니처 6 + 버전 2 + StartHeaderCRC 4 + NextHeaderOffset 8 + NextHeaderSize 8 + NextHeaderCRC 4 = 32. CRC는 뒤 20바이트(오프셋 12~31)를 덮는다. 모두 0인 시작 헤더는 버전이 0.0이 아니면 참으로 취급(근거 약함, 의미 미확인).

## 단계 4: 앞쪽 탐색 (SFX 등) 0x44db16~0x44dc3d
- 관측: 버퍼 `0x8020`바이트 할당(0x44daea), 읽은 32바이트를 버퍼 앞에 복사. 한 번에 최대 `0x7fe0`(첫 번째는 0x7fe0, 이후 +0x20)만 읽음(`mov edx,0x7fe0`, 0x44db30~0x44db3a), 남은 탐색량 `[ebx]-[ebp-0x24]`보다 크면 줄임(0x44db3d~0x44db5c).
- 관측: 읽은 구간에서 0x44dc55 호출. 0x44dc55는 바이트 하나씩 `0x37`, `0x7a`, `0xbc`, `0xaf`, `0x27`, `0x1c` 중 하나인지 분기하고, 후보 위치 `[ecx-1]=0x37, [ecx]=0x7a, [ecx+1]=0xbc, [ecx+2]=0xaf, [ecx+3]=0x27, [ecx+4]=0x1c`를 검사해 일치하면 위치 반환(0x44dc55~0x44dcbd).
- 관측: 후보마다 `push 0x14; lea ecx,[eax+0xc]; call 0x471330` 후 `cmp eax,[ecx+0x8]`(0x44dba0~0x44dbb6). 일치하면 0x44dbfe로 가서 32바이트를 `[esi+0x58]`로 복사하고 스트림 기준 위치(`[esi+0x40],[esi+0x44]`)에 찾은 오프셋을 더한 뒤, 스트림 객체 vtable `[edi+0x10]`(Seek로 추정)을 `위치+0x20`으로 호출(0x44dbfe~0x44dc33).
- 관측: 일치 못 하면 버퍼 마지막 0x20바이트를 앞으로 옮기고(`call ds:0x47c1e4`, memmove로 추정) 다음 구간을 읽는 루프(0x44dbd4~0x44db2d). 읽은 바이트 0이면 `push 1; pop esi`로 1 반환(0x44dbf9).
- 결과: 시작 위치에서 시그니처가 맞지 않으면 파일 안쪽으로 최대 탐색량까지 32KB 창을 밀면서 시그니처+CRC가 맞는 곳을 찾는다.

## 단계 5: 쓰기 쪽 대칭 (확인 가능한 범위)
- 관측: 0x450000이 `memcpy(this, 0x48e4e8, 6); this[6]=0; this[7]=4`(0x450002~0x450016) -> 쓰기용 시작 헤더 초기화(시그니처 + 버전 0, 4).
- 관측: 0x44ffd7 근처 `push 0x14` + CRC 호출 후 4바이트 기록(0x45001c), 8바이트 기록(0x45002b) -> 시작 헤더 쓰기(CRC는 20바이트 구간)로 추정.
- 호출처 0x44ffa9, 0x4500a4.

## 단계 6: 그 이후 (다음 헤더) — 미확인
- 다음 헤더 오프셋·크기·CRC를 읽어 검증하는 코드는 이 세션에서 찾지 못했다(`[esi+0x64]`, `0x6c`, `0x74` 참조는 다른 객체와 섞여 후보가 많음).
- 오류 메시지는 포인터 표(파일 0x7e6bc~0x7e704, VA 0x47f6bc~)로 참조되어 코드에서 직접 `push 문자열`로 참조되지 않음(단 "There is some data block after the end of the archive"만 0x430d24에서 직접 참조).
